# SageRead Agent 评测方案（从 0 到 1）

> 面向没有评测经验的人，也面向接下来的 Agent 重构 A/B。
> 一句话：**评测 = 固定题库 + 可重复运行 + 明确判分 + 记录成本。先测基线，再改，再对比。**

## 0. 为什么不能只靠「用起来感觉不错」

Agent 的输出是非确定的、多步的、答案开放的：

- 同一个问题，可能走 3 步也可能走 8 步；
- 可能找对了章节但总结错了，也可能总结对了但引用了不存在的段落；
- 可能今天对、明天错（模型/温度/上下文长度变化）。

所以「感觉不错」无法回答：**改了工具之后，是变好了还是变差了？哪一类问题变差了？多花了几步/token？** 评测就是把这个判断变成可重复的数字。

## 1. 工业界怎么评编码 Agent（可借鉴的部分）

- **SWE-bench / Terminal-Bench 类**：给 Agent 真实任务 + **隐藏测试**，跑完用测试判定，同时记录轨迹（用了多少步、改了多少文件、是否卡死）。核心是「结果判定 + 轨迹指标」。
- **Anthropic 的工具设计方法**：工具设计是评测驱动的——先做原型，建真实多步任务评测，持续迭代；指标不只看准确率，还看**工具调用数、总 token、单次耗时、错误率**；把失败轨迹（transcripts）交给 Agent 反向重构工具与描述；保留 held-out 防过拟合。
- **DeepSeek Harness 本身没有公开的内部评测方案可抄**；我们从源码能看到的是评测驱动留下的工程痕迹（工具超时策略、重复调用提醒、结果裁剪、图片预算等）——这些规则本身就是对失败模式的回应。对 SageRead 来说，关键是**建立自己的题库与基线**，而不是找一份通用评测表。

## 2. 评测的三层（从便宜到真实）

| 层 | 评什么 | 要不要模型 | 频率 | 成本 |
|---|---|---|---|---|
| L1 工具级 | 单个工具输出的结构/坐标/文件存在性/图片 MIME/预算上限 | 不要 | 每次改动 / CI | 秒级 |
| L2 Agent 级 | Agent 在固定问题上的工具序列 + 最终答案 + token/步数 | 要 | 每周 / 重构前后 | 分钟级 |
| L3 产品级 | 真实 UI 流程（滚动、位置、图片、面板） | 不要（UI 自动化） | 发版前 | 分钟级 |

三层互补：L1 保证「零件没坏」，L2 保证「装配后真的会干活」，L3 保证「用户看得见的地方没坏」。

## 3. 评测什么指标

### 3.1 能力（答得对不对）

- **任务成功率**：按判分器判定通过 / 总题数；
- **锚点命中率**：返回/引用的锚点（章节、图号、chunk）是否命中金标；
- **引用可定位率**：回答里的引用能否在原文中定位（工具返回坐标 + 原文核对）；
- **事实准确率 / 不编造率**：关键事实是否出现、是否出现原文没有的断言；
- **图表问答正确率**：图号、图注、方向/颜色/趋势等视觉事实；
- **无索引兜底成功率**：未建索引的书/论文上仍能按目录/位置读原文；
- **拒答正确率**：库里没有/超出范围时是否明确说不知道，而不是编。

### 3.2 效率（划不划算）

- 工具调用次数（steps）；
- 输入 / 输出 token；
- 首 token 延迟、总时延（p50/p95）；
- 工具错误率（参数错误/空结果/超时）。

### 3.3 稳定性（靠不靠得住）

- 同一题重复 3 次的答案一致率；
- 工具序列的方差；
- 不同模型（DeepSeek Flash / 本地模型）下的退化幅度。

## 4. 题库怎么建（第一版 30–50 题）

### 4.1 六个类别（每类 5–10 题）

| 类别 | 示例问题 | 金标 | 判分 |
|---|---|---|---|
| 定位与结构 | 「总结第 3 章论点」「论文的方法节在哪」 | 章节锚点 + 要点 | 锚点 + LLM rubric |
| 阅读与总结 | 「这一节讲了什么，用 5 句话」 | 要点 checklist | claim checklist + rubric |
| 跨文献 | 「比较 A、B 两篇的方法差异」「找三篇讨论 Y 的论文」 | 论文 id + 要点 | 检索命中 + rubric |
| 图表 | 「图 3 说明了什么」「图注是什么」 | 图号 + 图注 + 视觉事实 | 图号精确 + rubric |
| 位置 | 「我读到哪」「把当前这一节原文给我」 | 位置坐标 + 原文片段 | 坐标容差 + 片段命中 |
| 兜底/拒答 | 「这本书里有没有提到 Z」「没建索引的论文总结一下」 | 正确说没有 / 仍能读 | 拒答正确 + 兜底成功 |

### 4.2 单题的数据结构（建议放在 evals/tasks/*.yaml 或 json）

    任务：
      id: paper-figure-3
      category: figure
      doc_ref: { kind: paper, id: "<固定 fixture 的 paper id>" }
      prompt: "论文图 3 说明了什么？"
      gold:
        anchors: ["figure:<paper_id>:3"]
        facts: ["循环稳定性", "200 圈容量保持率"]
        must_not: ["编造的数值"]
      grader: { type: "anchor+rubric", rubric: "图号正确 1 分；图注/视觉事实 2 分；引用 1 分" }
      budget: { max_steps: 12, max_tokens: 20000 }

### 4.3 题库从哪来

- **固定 fixture 库**：在 dev 数据里选 2 本书（一本已索引、一本未索引）+ 3 篇论文（一篇长文、一篇图表多、一篇短），记录 id 与关键内容；不要让题库随用户书库漂移。
- 金标由 1 人起草 + 1 人复核（或 LLM 起草 + 人工逐题确认）；至少 20% 双人标注，计算一致性。
- 留 20% 题作 held-out，只用于最终验收，不参与迭代。

## 5. 三层怎么跑

### L1 工具级（不调模型，先做）

复用仓库已有的 CDP 验证脚本模式（scripts/cdp-verify-reading-position.mjs、cdp-verify-time-awareness.mjs）：

- 通过 CDP 在 dev 页面里 import("/src/...") 调工具/服务，或直接 invoke Rust 命令；
- 断言：返回 schema、绝对路径存在、图片 MIME 正确、锚点格式、offset 可续读、预算上限、错误码可操作；
- 跑完输出 ok/FAIL 列表，退出码非 0 视为失败。

这一层能在重构中第一时间发现「坐标算错/图片路径错/越界」这类硬故障。

### L2 Agent 级（要调模型）

两种跑法：

1. **UI 驱动（最真实）**：CDP 打开 dev 实例 → 新对话/指定文档 → 输入 prompt → 等待完成 → 从 threads 表（get_thread_by_id）或 DOM 取最终回答与工具调用序列。优点：和用户路径一致；缺点：UI 状态、流式等待、慢。
2. **直连 Agent harness（最快）**：Node 里复用相同的工具集 + 系统提示词 + 模型配置，直接跑 AI SDK，抓工具轨迹。优点：快、可控；缺点：和 UI 不完全一致（上下文注入、图片处理差异要单独校验）。

建议：**重构期用 2 跑 A/B（旧工具集 vs 新工具集），发版前用 1 做冒烟**。

### L3 产品级（发版前）

CDP 脚本覆盖关键交互：聊天滚动扩展（本次已写临时验证）、阅读位置跳转、图表 tab、图片引用、设置页模型选择。每次发版跑一遍，录屏/截图存证。

## 6. 判分器怎么做

1. **精确类**：锚点/图号/章节号/chunk id → 字符串或 id 精确匹配（可容忍格式归一化）。
2. **事实类**：claim checklist——必须出现的关键词/数值/结论，以及 must_not 中的编造内容；命中率 ≥ 阈值算过。
3. **开放类**：LLM rubric judge——固定 judge 模型、temperature 0、盲评（不告诉它哪个是新版）；每维度 0–2 分（事实、引用、完整、不编造），总分 ≥ 阈值算过。
4. **A/B 对比**：同一题分别跑旧/新，pairwise 让 judge 选更好（或打平），统计胜率；同时报告客观指标（步数/token/错误率）。
5. **人工抽检**：10–20% 的题人工复核，校准 judge；judge 与人工不一致率 >20% 时先修 rubric。

## 7. 结果怎么记

每次跑生成一个目录：

    .tmp-eval-runs/2026-10-22T10-00-00/
      results.json      # 每题：答案、工具轨迹、步数、token、时延、判分
      report.md         # 汇总表：成功率、锚点命中、平均步数、token、p95、错误率
      transcripts/      # 失败题原文轨迹，供反向改工具/提示词

report.md 至少包含：

- 总题数 / 通过数 / 成功率（mean ± std，3 次）；
- 分类别成功率（定位/总结/跨文献/图表/位置/兜底）；
- 平均工具调用数、平均 token、首 token 延迟 p50/p95、工具错误率；
- A/B 对比：胜/平/负、客观指标变化；
- Top 10 失败题与初步归因（工具选错/参数错/没读到/编造）。

## 8. 分阶段落地（贴合本次重构）

### Phase 0（发版后、重构前，半天）

- 选 10 道题（每类 1–2 道），人工跑一遍旧工具集，记录步数/token/答案；
- 这 10 题就是基线，不做 judge，先人工判分；
- 同时把「回图/路径/库地图」P0 的验收题定下来。

### Phase 1（P0 落地时，1 天）

- 写 L1 工具级脚本：read_image 本地路径、getFigures 绝对路径、库地图注入、guidance 可见性；
- 复用 CDP 脚本风格，输出 ok/FAIL；
- 加 15 题 L2 冒烟，只跑新工具集（不 A/B），确认没退化。

### Phase 2（P1 收敛时，2–3 天）

- 扩到 40–50 题，跑旧 vs 新 A/B，3 次重复；
- 验收门槛（建议）：
  - 任务成功率不低于基线 −2pp；
  - 锚点/引用可定位率不低于基线；
  - 跨文献/长阅读任务的中位步数或 token 下降 ≥20%；
  - 工具错误率 <2%；
  - 首 token 延迟不比基线差 20% 以上。
- 不达标就回退单点改动，而不是整体推翻。

### Phase 3（每次发版）

- L1 全量 + 10 题 L2 冒烟 + L3 关键流程；结果归档，形成趋势。

## 9. 常见坑

- **模型随机性**：temperature 0 + 3 次重复；报告方差，别看单次。
- **judge 偏见**：盲评、固定 judge、pairwise 优先；人工抽检校准。
- **题泄露/过拟合**：held-out 20%，不要拿验收题反复调提示词。
- **UI 不稳定**：等待完成而不是固定 sleep；失败重试 2 次并记录。
- **题库漂移**：固定 fixture 文档与 id；升级数据格式时同步更新金标。
- **成本失控**：先在 10 题上跑通；L2 用 DeepSeek Flash 等便宜模型；本地模型只做补充。
- **prompt cache 干扰**：A/B 时保持系统提示词前缀稳定，避免缓存差异污染时延指标。

## 10. 第一版最小行动（建议明天就能做）

1. 建 evals/ 目录：tasks/、fixtures/（记录 fixture 文档 id 与关键内容）、README。
2. 选 10 题，写清金标（锚点/要点/禁编内容）。
3. 用现有 CDP 脚本模式驱动 dev 实例跑 10 题，结果手写进 report.md。
4. 重构前跑一次，得到基线；之后每完成一个 P0/P1 改动跑一次。

> 评测不是学术仪式，是重构的安全带：**没有基线，就没有资格说「更优雅了」。**
